# ADR 0004: restricted local database and reviewed migrations

Status: implemented and locally verified, 2026-10-06. Scope: BOOT-02, with BOOT-01 browser boundaries and DOC-01/DOC-02 evidence obligations. This does not accept a full product requirement.

Keep the existing bootstrap administrator/database and VS Code volume untouched. Create separate managed local/test databases with environment-specific migration/API/match/worker roles. Migration roles own their database; runtime roles have only CONNECT, their schema USAGE and table CRUD. Revoke PUBLIC database CONNECT/TEMP, schema privileges and routine EXECUTE defaults for managed databases. Runtime roles receive no DDL, TRUNCATE, other-service schema or migration-journal access. Restricted credentials remain in ignored mode-600 local storage; app wiring is deferred until real domain integration.

Use checked-in numbered SQL with SHA-256 journal validation, one transaction and a database advisory transaction lock. Require the applied journal to equal a prefix of checked-in history. This adds explicit checksum and rollback evidence beyond simply recording an applied migration name. Typed Drizzle schemas/query helpers describe the synthetic service probes only. [Drizzle migration documentation](https://orm.drizzle.team/docs/migrations) permits manually managed SQL; the selected pg adapter is described in [the PostgreSQL adapter documentation](https://orm.drizzle.team/docs/get-started-postgresql). The installed pinned API must be verified in actual package builds/tests.

Compared with adding Drizzle Kit now, reviewed SQL needs no schema generation tool or build-script allowances and makes role/grant effects reviewable. Compared with one shared runtime role, distinct identities make cross-service and cross-environment denials testable. Compared with rebuilding the Director's current Compose service, a disposable project/volume proves recreation without disturbing existing data. The test proves the same pinned image/mount/network model, not a recreation of the existing PC volume or a backup/restore drill.

PostgreSQL default privileges affect only future objects created by the specified owner; they do not replace grants on existing tables. Schema-scoped revocation cannot undo globally granted routine EXECUTE, so revoke it globally for each managed migration owner. See [PostgreSQL 18 default privileges](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html) and [GRANT](https://www.postgresql.org/docs/18/sql-grant.html). Tests verify effective access with each actual login.

Only explicitly named local/test targets are accepted. Existing roles/databases are changed only if their ownership marker identifies this provisioner, and drifted role attributes/membership/ownership are rejected. Provisioning is repeatable for marked objects; a crash between CREATE DATABASE and its separate ownership comment requires deliberate ownership/provenance inspection before recovery, and retries intentionally refuse the unmarked database; migrations are explicit, transactional and not run by app startup. Production roles, RLS, domain grants, destructive migration policy, backup/restore and deployment credentials require later work.
