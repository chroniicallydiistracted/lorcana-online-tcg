# Durable synthetic match commands

PLAY-01 follows [ADR0013](../adr/0013-durable-synthetic-match-commands.md), the [execution plan](../plans/2026-10-13-play-01-durable-commands.md) and [qualification](../validation/play-01.md). Run application commands inside the committed Dev Container. The application interface lives in `apps/match-service/src/service.ts`; Fastify still exposes diagnostics only. No game listener or auth-free transport is added.

## Interfaces and authority

`createMatchService({repository,releases,executor?,now?})` requires a trusted retained `ReleaseRegistry` with an active built foundation engine and protocol1. `create({matchId,players})` accepts exactly two distinct bounded ASCII identifiers, captures server time, generates a private cryptographic seed and writes a synthetic non-rewarding match. Existing identity with identical participants/release/engine returns the existing match; conflicting reuse fails. It returns only match/version/release metadata.

`submit(trustedActor,{matchId,commandId,expectedVersion,move,input})` keeps actor authority outside the request body. Plain closed own-data objects, safe unsigned counters, ASCII IDs up to80 characters, moves up to64 characters and copied input are mandatory; the canonical full semantic intent is limited to16KiB. Malformed input fails `INVALID_REQUEST` before durable writes. Participation is checked against storage. `(matchId,actorId,commandId)` and the canonical intent hash identify a receipt: identical retry returns it with `duplicate:true`; altered content/version fails `ID_CONFLICT`. Receipt metadata contains no private checkpoint, seed, game state or logs.

Only `chooseWhoGoesFirst`, `alterHand`, `putCardIntoInkwell`, `playCard`, `quest`, `questWithAll`, `challenge`, `moveCharacterToLocation`, `activateAbility`, `resolveBag`, `resolveEffect`, `passTurn` and `concede` may reach the kernel. The same browser-safe policy guards Lab. Every manual/debug move, `forfeitGame`, unimplemented server-only `sing`/`singTogether` and unknown/prototype names is refused. Advanced Sandbox does not gain a generic debug bypass; future manipulation operations need explicit authority and reward isolation.

## Commit and recovery

`createMatchRepository(target)` uses the restricted match login only. Migration0002 adds private releases/matches/receipts/journal/outbox; append-only0003 strengthens outcome/identifier constraints after0002 was actually applied during development. Never edit previously applied SQL. Apply reviewed history first to test, then local using [database operation](database.md). API and idle worker roles cannot read these tables.

The service checks durable receipts, participant membership and exact synthetic engine/rules/catalog/format/protocol/release pins. A bounded owned Node worker re-executes the private checkpoint and computes a speculative command outside any database transaction. A short transaction locks the match row and explicitly compares version/checkpoint, then writes state, accepted journal, receipt and metadata-only outbox atomically. Acceptance returns after COMMIT. A competing candidate becomes stale and is discarded. SQL failure rolls everything back. Lost acknowledgement is resolved by retrying the same identity, never inventing another command ID.

Receipts support accepted, rejected (`forbidden`/`invalid_intent`) and stale (`stale_state`) results. Invalid engine intentions and forbidden names have stable receipts but never change authoritative state. Worker/deadline/pin/checkpoint/storage failures fail closed with fixed `UNAVAILABLE`/`PIN_UNAVAILABLE`/`FORBIDDEN` errors and no new receipt. No outbox dispatcher or economic consumer is implemented. Outbox holds event identity, match/version and changed/completed kind; one terminal event is enforced. PLAY-03 owns authorized publication.

`createPrivateMatch({matchId,players,startTimestamp})` and `restorePrivateMatch({archive,digest},expectedMatchId)` are server-private engine functions. Checkpoints are copied canonical transcript bytes and a distinct integrity digest, bound to logical match and current compiled code including the player policy. Restoration reconstructs every command/result/random outcome/state hash. Capture and restore enforce2MiB,2048 attempts and shared cumulative tree bounds. Failure never commits an unreadable candidate. The digest is a trusted-storage anchor, not a caller-supplied authentication signature. Ordinary qualification handles still have no live checkpoint/seed export; D10 recipient delivery remains AUTH/REPLAY work.

Executor defaults are2 active workers,32 queued jobs and5-second execution/queue limits. Workers have64MiB old/16MiB young/4MiB stack ceilings, sanitized environment, preserved source export conditions and drained/discarded upstream output. Each candidate resolves after its worker terminates. Idempotent close rejects queued work and awaits owned termination; `service.close()` then closes its DB pool. These are foundation limits, not measured production capacity. Wall time is floored at last committed time; game-clock policy belongs to PLAY-04.

## Verification

After reviewed migrations, use `pnpm test:match-integration`: three real storage constraints and ten service scenarios use isolated test-role fixtures. Scenarios prove independent same-version candidates, stable retries/actor isolation, exact pins and corrupt checkpoints, actual journal/outbox SQL failures, and SIGKILL before COMMIT and after COMMIT/before response with fresh-process recovery. Tests delete only their owned match fixtures. `pnpm verify:foundation` remains DB-free for clean installation; it includes private replay/policy/worker unit regressions. The disposable CI pipeline runs live match tests after both DB migrations and role checks.

Fixture release manifests use actual built hashes and an explicitly simulated creation time; they are not promoted releases. Preserve every native red/green receipt. Never print/assert-diff private archives. Check owned children/pools/listeners after verification. Current-only synthetic restore does not supply retained production engine loaders, authenticated transport, viewer/log privacy, full catalog/rules certification, multiplayer or player-facing admission.
