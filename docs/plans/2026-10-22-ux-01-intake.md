## Boundaries to preserve

- **Ownership (§32).**
  - `packages/design-system` owns primitives, shared component behavior and stories.
  - `packages/presentation` owns Babylon scenes, finishes and choreography.
  - `apps/web` owns routes and room composition.
  - The design system must not pull Babylon into ordinary controls.
- **Data.**
  - Reference positions are presentation fixtures built from real catalog printings. They do not run the engine, and they carry visible demonstration labels (§24, §33).
  - Engine and rules tests keep their synthetic fixtures (D25).
  - Browser code imports no engine kernel, private state or server code.
- **Card presentation.**
  - The fan-content notice stays reachable from every screen.
  - `officialAssets` keeps the neutral takedown fallback working on every screen.
  - Foil printings show a static finish marker. CardFX integration needs its own qualification (§16) and an ADR (§32), and is out of UX-01 scope.
- **Dependencies.** No new dependency without pinning in its owning workspace and passing the license gate.
- **Workspace.** One heavyweight qualification at a time, in the existing Dev Container. `.env.local`, `.local/database.json`, the database volume and the Director's root file are untouched.

## Questions for the Director

Each question carried the agent's recommendation. The answers follow the questions.

1. **Direction studies.** The backlog and blueprint §11.1 ask for three alternative studies. The adopted standard (D17) already fixes one direction (§2, §4–§12), and §36 asks for one matched set. Recommended: one matched set of the four screens under the standard, with the Director's approval recorded as the reference-direction selection.
2. **Medium.** Recommended: interactive reference screens composed in the design system's Storybook from the built components and real catalog cards, labeled as demonstrations. This keeps demonstration data out of `apps/web`; the WEB tasks later compose the real rooms there from the same components. Alternatives: reference routes in `apps/web`, or static mockups before code.
3. **Match table.** The 2.5D Babylon table belongs to WEB-01. Recommended: build the crowded match as the Flat tier (§30), a DOM board with every zone, marker, prompt and panel. Every tier must keep this complete layout, and scene depth and lighting follow in WEB-01. Alternative: include a first static Babylon scene now, which brings renderer work forward.
4. **Ink forms.** §4 places large authored ink forms at room perimeters. No such artwork exists. Recommended: leave documented, quiet slots so the screens are judged on composition, and supply or commission the artwork separately. Alternatives: provisional vector forms drawn by the agent and labeled provisional, or artwork supplied by the Director.

Consequences for the written design, from the existing boundaries:

- The scene code belongs to `packages/presentation`, which already pins `@babylonjs/core` 9.29.0. Design-system components stay free of Babylon (§32). Only the match reference story uses the scene, through a lazy boundary and a development-only workspace dependency, as the stories already use `@lorcana/rules-data`. The design decides whether ADR 0017 needs an amendment for this dependency.
- The scene is a static reference for composition and look. WEB-01 still owns the scene lifecycle, quality tiers, measured frame times and GPU-context restoration. UX-01 makes no claim about any of these.
- The Flat tier stays required (§30). The semantic board, which screen-reader and keyboard users rely on (§19, §25), and the DOM presentation of the same position remain part of the match reference. Scene and DOM read one presentation fixture, so they cannot disagree.
- Chromium automation renders WebGL in software. Browser checks of the scene are limited to presence, fallback and accessibility. Visual comparison of the scene is a human review, not an automated pass.

Defaults that need no answer unless the Director objects:

- **Viewports.** Desktop 1440 × 900, tablet landscape 1180 × 820 and tablet portrait 820 × 1180, in Paper and Ink, at comfortable and compact density where it applies. Desktop and tablet come first under D17. Phone journeys stay staged in UX-02.
- **Required states.** The states are the §34 fixtures:
  - large and small hands;
  - long card and player names;
  - mixed normal and foil printings;
  - empty, partially owned and unavailable Collection data;
  - binder resizing and printing navigation;
  - deckbuilder invalidity, ownership limits and unsaved work;
  - pack skip and interruption;
  - the §21 non-success states that apply to each screen.
- **Interaction specification.** For each screen: its state machine (§20 for the match, §23 for packs), keyboard, pointer and touch operation, focus order and restoration, live announcements (§25), the required confirmations (§20) and reduced motion (§26).

## Qualification design

These checks are completed after the answers and the written design.

- **Static.** Typecheck, lint, token, style and component-contract gates, documentation contracts, and a story for every documented state of each new component and reference screen.
- **Chromium automation.**
  - axe WCAG 2.2 A/AA on every reference story in Paper and Ink;
  - 44 px targets, focus visibility and contrast;
  - keyboard journeys through each screen's main task;
  - dialog containment and restoration;
  - 320 px reflow of panels and 200% text;
  - reduced motion and forced colors;
  - takedown fallback on every screen.

  All of this runs in the `design-system` job, through `pnpm evidence:run` and `python3 scripts/ci-local.py --suite design-system`.
- **Visual review.** Captures of each screen and state at the declared viewports in both themes. The agent first reviews them against the §33 rejection criteria; the Director then reviews them for approval.
- **Not claimed.**
  - real browsers and devices (UX-02);
  - manual accessibility journeys;
  - performance and the scene (WEB-01);
  - live gameplay and the match interface (WEB-02);
  - pack economics (ECON-02, WEB-03);
  - Stable component status, which needs this evidence plus UX-02 (§35).
